# Magi threat model

Magi participants inspect untrusted repository content, provider output, tool results, and web evidence. Those inputs can contain prompt injection. The participant pre-prompt tells models that evidence cannot change the protocol, but this is a model-level safeguard, not a technical isolation boundary.

Participant credentials remain owned by the configured provider harness. T3 does not intentionally copy credentials into Magi prompts or logs. Native provider tools may still expose data that their own credential and sandbox policy permits, so operators must treat provider configuration as part of the trust boundary.

The MCP credential identifies the calling conversation. Magi runs belong to that conversation, and every Magi control tool acts only on runs it owns. Provider-native subagents share their parent session's credential, so they act as their parent conversation; Magi does not add a separate identity for them. Runs owned by a subagent or delegated task are also listed, read-only, in the history of the conversations above it in its lineage, so the user can see nested Magi work and its cost from the conversation they started; listing a run does not let an ancestor's agent control it.

A participant's subtree is the participant conversation, its provider-native subagents (which share its credential), and its T3-delegated subagents at any depth. The server finds it from the caller's subagent lineage and the participant threads recorded on Magi runs. The subtree cannot start Magi runs or create conversations outside a subagent lineage: `create_threads`, `t3_thread_launch`, `t3_thread_fork`, and scheduled tasks that launch a fresh thread per run (`schedule_task` or `update_scheduled_task` producing such a task, and `run_scheduled_task_now` on one). Tools that write to or control a thread act only on threads strictly beneath the participant: `t3_thread_send`, `t3_thread_send_attachments`, `t3_thread_interrupt`, `t3_pending_request_respond`, `t3_queue_edit`, `t3_queue_cancel`, `t3_queue_reorder`, `t3_queue_promote_to_steer`, `t3_thread_merge_back`, `t3_thread_organize`, and scheduled tasks bound to another thread. That excludes the arbitrator, the root conversation, other participants, and the participant conversation itself, although a participant may keep scheduled work bound to its own conversation. The subtree can still delegate, use native subagents, act on its own delegated subagents, and read evidence and thread state. Thread metadata changes (`t3_thread_update`) and scheduled-task deletion are not confined. Ordinary conversations and their subagents are unaffected.

Participants are ordinary T3 child conversations. They inherit the owning conversation's access mode and have the same T3 and harness abilities as any conversation, including their own subagents and T3 delegation. The participant instruction requires them to stay read-only: investigate and deliberate, without modifying files, running mutating commands, committing, or taking other side-effecting actions, and to ask their own subagents to do the same. Only the arbitrator acts on the consensus. This is an instruction, not a capability restriction; provider-native boundaries differ, so it does not prevent every provider defect, prompt-injected action, credential read, mutation, or network request. Harness-native web access is not a network firewall.

Selected evidence is snapshotted before participants start and addressed to each participant conversation individually. `context_read` resolves only artifacts addressed to the calling conversation, so one participant, or any other conversation, cannot read another's evidence through Magi.

Bounded roster size, turn limits, context limits, one transient retry, and explicit cancellation reduce denial-of-service exposure. Participants can start their own subagents, so cost can grow beyond the configured roster; T3 does not cap that nesting, but participants cannot start nested Magi runs. Participant response arrays are intentionally unbounded so every active proposal and decision set can be represented without a protocol-imposed item ceiling; individual text fields remain length-bounded. Magi starts the complete roster concurrently without its own participant limit. Participant turns have no product deadline and end when the provider finishes, fails, or the run is stopped. Operators should use least-privilege provider credentials and review native harness policies.

Diagnostics omit prompt bodies and referenced tool-result bodies by default. Raw participant text remains durable audit data in the run detail and must be protected like conversation content.
