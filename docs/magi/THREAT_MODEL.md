# Magi threat model

Magi participants inspect untrusted repository content, provider output, tool results, and web evidence. Those inputs can contain prompt injection. The participant pre-prompt tells models that evidence cannot change the protocol, but this is a model-level safeguard, not a technical isolation boundary.

Participant credentials remain owned by the configured provider harness. T3 does not intentionally copy credentials into Magi prompts or logs. Native provider tools may still expose data that their own credential and sandbox policy permits, so operators must treat provider configuration as part of the trust boundary.

The MCP credential identifies the calling conversation. Magi runs belong to that conversation, and every Magi control tool acts only on runs it owns. Provider-native subagents share their parent session's credential, so they act as their parent conversation; Magi does not add a separate identity for them. A run started by a subagent or delegated task stays with that owning conversation. Participants appear as ordinary subagents in its Lineage; Magi does not hoist their run or conversations to ancestors.

A participant's subtree is the participant conversation, its provider-native subagents sharing its credential, and its T3-delegated subagents at any depth. The server finds it from local subagent lineage and the participant threads recorded on Magi runs. The subtree cannot start Magi runs or create conversations outside a subagent lineage through `create_threads`, `t3_thread_launch`, or `t3_thread_transfer` with action `fork`. It also cannot create, rebind or run scheduled tasks that launch a fresh thread per run. `schedule_task` handles both creation and update; `run_scheduled_task_now` checks the existing task's target.

The guarded local operations act only on threads strictly beneath the participant: `t3_thread_send`, `t3_thread_send_attachments`, `t3_thread_interrupt`, `t3_workflow_stop`, `t3_pending_request` with action `respond`, the mutating `t3_queue` actions, `t3_thread_transfer` with action `merge_back`, `t3_thread_organize`, and scheduled tasks bound to another thread. That excludes the arbitrator, the root conversation, other participants, and the participant conversation itself. A participant may keep scheduled work bound to its own conversation. The subtree can still delegate locally, use native subagents, act on its local delegated subagents, and read local evidence and thread state. Thread metadata changes through `t3_thread_update`, model selection through `t3_thread_configure`, and scheduled-task deletion use ordinary access checks without Magi participant confinement. Ordinary conversations and their subagents are unaffected.

Linked-environment forwarding replaces the calling conversation's credential with the link's credential. The peer cannot enforce its Magi participant lineage. The forwarding service therefore refuses linked-environment use by participants and their descendants before making a peer request, including reads, remote delegation and link discovery. Local link management through `t3_environment_link` and `t3_environment_unlink` uses ordinary full-access checks without Magi participant confinement; these operations do not forward calls through a link. Link requests require the user's answer. Local delegation and descendant control remain available. Ordinary nonparticipant callers retain the upstream linked-tool behavior. This boundary does not restrict harness-native network access.

Participant membership is not propagated to or retrospectively assigned to remote children. Their followers and cancellation calls retain the local parent scope and also encounter the forwarding refusal. If participant-created remote work already exists without that membership, cleanup requires ordinary user authority at its destination.

Participants are ordinary T3 child conversations. They inherit the owning conversation's access mode and retain local subagents and T3 delegation. The participant instruction requires them to stay read-only: investigate and deliberate, without modifying files, running mutating commands, committing, or taking other side-effecting actions, and to ask their own subagents to do the same. Only the arbitrator acts on the consensus. This is an instruction, not a capability restriction; provider-native boundaries differ, so it does not prevent every provider defect, prompt-injected action, credential read, mutation, or network request. Harness-native web access is not a network firewall.

Selected evidence is snapshotted before participants start and addressed to each participant conversation individually. `context_read` resolves only artifacts addressed to the calling conversation, so one participant, or any other conversation, cannot read another's evidence through Magi.

The user must explicitly supply the roster, consensus threshold, and turn limit. Missing or ambiguous configuration requires clarification. Magi applies no maximum roster size and no default threshold or turn limit. Only omitted voting weights default to 1. Explicit finite turn limits, context limits, one transient retry, and cancellation reduce denial-of-service exposure. Participants can start their own subagents, so cost can grow beyond the configured roster; T3 does not cap that nesting, but participants cannot start nested Magi runs. Participant response arrays are intentionally unbounded so every active proposal and decision set can be represented without a protocol-imposed item ceiling; individual text fields remain length-bounded. Magi starts the complete roster concurrently without its own participant limit. Participant turns have no product deadline and end when the provider finishes, fails, or the run is stopped. Operators should use least-privilege provider credentials and review native harness policies.

Normal tool results return each participant response once, in structured form when parsing succeeds. Raw participant text, protocol records, and referenced artifacts remain durable operational evidence and must be protected like conversation content.
