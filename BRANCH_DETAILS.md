# Subagent Threading Work

The Codex subagent-threading implementation covers subagent lineage, standalone persisted child-conversation projection and routing, opt-in default-web Agents-panel navigation, contextual Legacy Sidebar/mobile rows, exact active terminal subagent visibility on those lineage surfaces without hidden terminal ancestors, child-thread output isolation, child stop behavior, provider-control failure isolation, parent metadata ingestion, and related tests. `MessagesTimeline` and `AgentsPanel` own subagent lifecycle and activity presentation; this branch does not add custom in-conversation subagent tool-call boxes. Provider-native subagent activity, including Antigravity task batches, remains on its existing presentation path and does not become persisted child conversations.

Standalone web child-conversation visibility is off by default behind `Subagent conversations` in Settings → General. While it is off, the Agents panel remains the lifecycle roster but its rows are not child-conversation links; Default Sidebar search, the command palette, and Legacy Sidebar omit children; and a direct child route redirects to its immediate parent without subscribing to child detail. Enabling the setting restores those web navigation surfaces. Child shells, lineage, recursive running counts, and root-owned lifecycle behavior remain active regardless of the setting.

Thread archive/delete lifecycle behavior is enforced server-side in the orchestration decider and documented in `SUBAGENTS.md`. `apps/web/src/components/threadActionMenu.logic.ts` exposes settle, snooze, and delete only when `permissions.rootLifecycle` is true; `Sidebar.tsx` and `useThreadActionMenu.ts` derive that permission from the persisted relation and retain handler-side fail-closed guards. Subagent children therefore keep non-lifecycle actions such as pin, rename, unread, copy, and project settings without receiving root-only actions. The canonical sidebar filters unresolved selected keys and derives lifecycle permissions from the resolved set when opening a multi-select menu. `LegacySidebar.tsx` applies the same persisted-shell boundary to multi-select and single-row archive/delete and adds post-confirmation revalidation: unresolved or child selections hide the lifecycle affordances, bulk handlers re-read the unchanged selected keys and current shells before dispatch, and single-row handlers re-read the latest shell and fail closed before dispatch.

Child runtime events that arrive with parent-collab metadata may synthesize the missing child shell before their output/actions are ingested. `makeSyntheticSubagentThreadShell(...)` in `apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts` is the only constructor for those shells: it inherits parent project, model, runtime, interaction, branch, and worktree context; resets child-owned lifecycle, session, activity, and presentation fields; and satisfies `Required<OrchestrationThreadShell>` so shell-contract additions fail at this seam. Child stop requests must target the selected child turn when known, and if no active child turn can be identified the server records a child interrupt failure and marks the child stopped instead of falling back to the root session's active turn. Provider-control diagnostics are best effort during cleanup: a failed diagnostic append is counted and logged without preventing child relation/session cleanup or root session-stop terminalization after a failed provider request.

`apps/server/src/orchestration/ActivityPayloadProjection.ts` keeps transported `collab_agent_tool_call` activities compact while retaining the subagent fields consumed by client work logs and activity presentation: allowlisted streamed output chunk fields verbatim, prompt-bearing item and raw-input fields, tool/item ids, `kind`, parent-collab item/detail metadata, and child thread/parent item/title references. This preserves ordered lifecycle data and direct-child correlation without forwarding unrelated provider payload bulk.

`apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts` generates a child title only while the persisted child shell still has its seed or the generic `Subagent` title, then stores the generated title on that shell. The lineage sidebars, child conversation, and Agents panel therefore reuse one persisted generated title when standalone visibility is enabled. `apps/web/src/components/ChatView.logic.ts` scopes each provider agent id to a persisted child shell in the active environment and root lineage only after opt-in; `ChatView.tsx` uses that same record for both the Agents-panel title and navigation target. Direct-agent branches with running work sort above idle and finished branches, and descendants render immediately below their parent with capped lineage indentation.

`resolveRightPanelControlsOwner(...)` in `apps/web/src/components/ChatView.logic.ts` is the placement seam for right-panel title-bar controls, including the Agents panel. `ChatView.tsx` keeps them at the root while an inline panel is present, lets an open sheet own them in sheet layout, and falls back to the chat header otherwise. `ChatView.logic.test.ts` covers all three ownership states.

`apps/web/src/components/chat/SubagentControlBar.tsx` owns the standalone child conversation's running/terminal status surface and stop action. `ChatView.tsx` supplies the persisted relation and interrupt callback without duplicating that presentation inside the composer implementation.

`apps/mobile/src/features/threads/SubagentControlBar.tsx` owns the equivalent mobile child control and its reserved height. `ThreadDetailScreen.tsx` selects that control instead of the normal composer for persisted child shells.

`mapThreadSharedFields(...)` in `apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts` is the fold-back seam for projection-thread fields shared by full snapshots, command read models, shell snapshots, and detail reads. Keep the `parentRelation` mapping centralized there and retain its non-optional compile-time contract when changing the projection field list.

`mapThreadParentRelationFields(...)` in `apps/server/src/orchestration/Layers/ProjectionPipeline.ts` is the sole relation-to-column mapping for `thread.created` and `thread.meta-updated`. Keep both projection paths routed through it so root defaults and every subagent lineage field stay identical. Projection bootstrap replays every unapplied event rather than the event store's default 1,000-event window. `ProjectionPipeline.test.ts` holds that guarantee at the branch boundary by reconstructing a completed depth-two child after 1,000 earlier events and asserting its full persisted relation.

`apps/web/src/components/WorkspaceBreadcrumb.tsx` owns the optional `trailingAction` slot for controls adjacent to a breadcrumb. `apps/web/src/components/chat/ChatHeader.tsx` uses that slot for the child conversation's direct-parent action. Keep the action outside the breadcrumb `<ol>` so list semantics and the current thread's `aria-current="page"` remain intact, while preserving the parent-navigation callback, accessible label, icon, tooltip, and conditional visibility.

Migration `048_ProjectionThreadParentRelation` applies the branch's final lineage columns, root backfill, and indexes directly after the `base/main` migration tail. The branch has no compatibility migrations for intermediate branch builds because its upstream merge starts from the unmodified base schema.

Keep pending tasks outside `buildVisibleThreadLineage(...)`, keep recent-thread/fallback/active-row lineage flowing through `selectRecentThreadLineage(...)`, and retain exact active terminal child visibility and selected-child shells without restoring hidden terminal ancestors.

Logical project grouping must preserve lineage across every project reference in the selected group, including stale duplicate ids that resolve to a canonical physical project. `apps/mobile/src/features/home/homeThreadList.ts` groups those references before lineage traversal, retains the exact active terminal child while targeting new threads at the canonical project, and uses `buildHomeProjectTitleIndex(...)` to assign the logical group title to every member reference. `apps/mobile/src/features/home/HomeScreen.tsx` and `apps/mobile/src/features/threads/ThreadNavigationSidebar.tsx` use that shared title index for their thread rows; the navigation sidebar scopes `threadsForGrouping`, not the raw shell list, so a selected child shell synthesized from detail remains available to the lineage builder.

`getLatestThreadSortTimestamp(...)` in `packages/client-runtime/src/state/threadSort.ts` is the shared member-thread timestamp calculation for web sidebar project groups and mobile home project groups. Both clients reuse its member aggregation and malformed-timestamp behavior. Web calls it only for non-empty project thread lists and otherwise falls back to the project's timestamp; mobile may call it with an empty thread group before folding in pending-task timestamps.

Mobile Thread List v2 applies contextual visibility before active/settled/snoozed partitioning. Root conversations show a recursive running-descendant counter and keep every nested generation collapsed by default; toggling a counter reveals eligible running compact subagent status rows at their stored depth, and a nested subagent requires its own toggle before exposing the next generation. It preserves only the exact selected terminal child in the navigation sidebar without restoring hidden terminal ancestors or promoting or paging out settled lineages, keeps terminal descendants searchable by title as navigation-only rows, rebases search-result depth when filtered parents are absent, and keeps settled and snoozed lineage groups atomic while paging or shelving. Collapsing the settled shelf hides complete lineage groups, while a selected settled subagent remains directly navigable at its stored depth. Snoozing a root retains its eligible running descendants, stored depths, recursive running count, and expansion state in the snoozed shelf instead of promoting terminal children into the active list; only the snoozed root receives wake metadata. A nested subagent already snoozed by persisted state from another or older client shelves its subtree without hiding unsnoozed ancestors or siblings, rebasing the shelved subtree to depth zero; current row menus do not expose child lifecycle mutations. Snoozed counts count the independently snoozed threads, while counts, shelf membership, and wake metadata remain scoped to the active search.

Pin ordering is applied to pinned root-lineage groups on mobile, so user-arranged pin keys order whole lineages without flattening child rows out of their parent group.

The default web Sidebar renders root conversations only. A root with persisted running descendants or live provider-native agent tasks shows a bot indicator containing the greater of the recursive running-descendant total and the server-projected `activeSubagentCount`, with no disclosure arrow; clicking it navigates to the root when necessary and opens that conversation's Agents panel. The live-task projection retains a bounded settled-task tombstone until provider-session exit so late item or progress events cannot revive a settled count. A fresh start clears the tombstone, while explicit `running` or `waiting` updates may resume an idle task but not a hard-terminal one. Default Sidebar rows never render descendants, including the exact terminal child currently open. After standalone visibility is enabled, thread search collects complete depth-first lineages from active, snoozed, and settled roots in lifecycle order after logical-project scoping, so matching nested and terminal subagents remain directly navigable. The opt-in Legacy Sidebar and mobile Thread List v2 retain the contextual lineage/disclosure behavior described above, while the web Legacy Sidebar omits child rows when standalone visibility is disabled.

Pinned-thread ordering and reorder capability gating operate on the filtered root set before expanded child rows are flattened, preserving both user-defined pin order and subagent lineage.

For grouped project filtering, `selectSidebarProjectLineageThreads(...)` in `apps/web/src/sidebarProjectGrouping.ts` lives beside the logical-project snapshot selectors and scopes the non-archived structural shell list before root classification, running-descendant counting, explicit expansion, and search collection. Its project-key set must contain every stale and canonical project reference in the logical scope, so a parent and child stored under different physical project ids remain one nested lineage rather than separate root rows or disconnected search entries. Default Sidebar root classification, recursive counts, traversal, and search are isolated in `apps/web/src/components/SidebarSubagents.logic.ts`; `SidebarSubagentThreadRow` in `Sidebar.tsx` supplies only the running-count decoration to `SidebarThreadRow`, leaving the draft and project-settings Sidebar structure independent of lineage behavior.

`SUBAGENTS.md` contains the detailed implementation requirements.

## Development Ports

- Web: `5739`
- Server/WebSocket: `13779`
- Offset `6` is this worktree's reserved starting offset; do not reuse it for another
  concurrent worktree. Run the full stack with `T3CODE_PORT_OFFSET=6 vp run dev`.
  When running the split processes, prefix both `vp run dev:server` and
  `vp run dev:web` with the same setting.
- `T3CODE_PORT_OFFSET` is a raw port delta, so offset `6` prefers the ports above.
  The dev runner may shift unavailable ports; treat the actual server and web ports
  in its `[dev-runner]` output as authoritative. With split processes, if
  `dev:server` shifts away from `13779`, either free that reserved port and restart
  the server or pass the reported port to the web runner with
  `T3CODE_PORT_OFFSET=6 vp run dev:web --port <server-port>`.
