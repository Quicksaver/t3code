# Magi consensus orchestration

## Branch contract

Magi is an agent-operated, provider-neutral weighted consensus workflow inside one V2 conversation. The conversation's agent is the arbitrator. It prepares and starts a run only when the user explicitly requests Magi. Participants are ordinary delegated subagent conversations. There is no Magi panel, arming state, first-message arm, run-history UI, timeline card, diagnostics view, or ancestor audience.

The user must explicitly supply the roster, consensus threshold, and turn limit. Missing or ambiguous values require clarification before starting. A request such as "Run Magi on the question 'is X really Y?'" does not authorize inventing those values. Omitted participant weights default to 1, the only Magi configuration default. The roster has at least two participants and no Magi-specific maximum. Explicit model selections and their supported traits are preserved.

`MagiStartInput` requires the complete run configuration, and the service decodes it again before context lookup, replay, persistence, or dispatch. The default arbitrator prompt and fixed tool protocol require clarification. A custom arbitrator prompt cannot relax schema or service validation.

## Ownership and authority

The owner is the conversation identified by the calling MCP credential. Provider-native subagents sharing that credential act as that conversation. A T3 delegated task owns its own run and participant children. Runs and participants are never hoisted into a grandparent's history or Lineage. Lineage shows participants through the same graph and navigation behavior as ordinary subagents, without Magi-specific filtering or grouping.

Magi supplies consensus procedure, never action authority. Advice requests produce recommendations. The arbitrator executes threshold-approved work only when the initiating user request independently authorizes execution, under its normal permissions and approvals. Participants are instructed to investigate read-only and pass that instruction to their subagents. This is a prompt instruction, not a filesystem sandbox.

The fixed electorate is validated in full before creation or further deliberation. An unavailable provider, model, or option rejects the whole roster without persistence or dispatch. The arbitrator follows explicit user instructions for unavailable participants; otherwise it pauses an existing run and asks the user. Failures, refusals, abstentions, malformed answers, and context exhaustion never reduce the denominator or trigger automatic substitution or reweighting.

`MagiParticipantPolicy` retains indexed membership and walks ordinary subagent lineage to restrict participant subtrees. Participants and their descendants cannot start Magi recursively, launch top-level conversations, or send/control work outside their own descendants. Native subagents share the parent's credential. Ordinary nonparticipant conversations remain unaffected. The detailed capability boundary and its exceptions remain in `docs/magi/THREAT_MODEL.md`.

Archiving/unarchiving an owner cascades to its participants. Deleting the owner cancels active work, removes participant conversations, and deletes the owner's Magi records and context grants. Stopping a run interrupts future work without rolling back completed actions.

## Configuration and discovery

`magi_get_options` derives the caller's project and returns available V2 provider instances, models, traits and validation bounds. Whole-roster preflight honors project-level provider enablement. Settings keep only arbitrator instructions; they contain no remembered roster, threshold, turn limit, or diagnostics preference. Web/desktop settings retain connected-environment selection and settings-write permission handling.

Thresholds are integer percentages from 1 through 100. `requiredWeight = ceil(totalWeight * thresholdPercent / 100)` must exceed half of the fixed electorate weight. Voting weights are integer 1 through 100. Participant ids are unique; duplicate model configurations are permitted. Explicit `null` or `0` turn limits mean unlimited, normalized to `null`. A finite limit is an explicit nonnegative integer, and 0 is its unlimited alias. No missing turn limit becomes unlimited or one turn.

Settings edits affect future runs. Each existing run keeps its model selections, weights, arbitrator instructions, threshold, and limit snapshot. No separate arbitrator model exists. Draft hydration removes obsolete magiArm configuration from web and mobile persistence while retaining ordinary drafts and signed-out drafts.

## Agent protocol and evidence

The agent tools are `magi_get_options`, `magi_list_context_activities`, `magi_start`, `magi_deliberate`, `magi_get_turn_result`, `magi_record_arbitration`, `magi_record_actions`, `magi_control_run`, `magi_get_terminal_proposals`, `magi_recover_turn_result`, `magi_recover_run_context`, and `context_read`. Client RPCs are only `getSettings`, `updateSettings`, and `resetSettings`.

Before a start or deliberation call, gather intended evidence as completed tool activities and immediately discover their T3 activity ids with `magi_list_context_activities`. Provider-native tool ids are not portable evidence references. Maintain a mapping from each intended evidence role to a distinct completed activity. The service validates ownership, completion, uniqueness, and size, then snapshots complete selected results under deterministic artifact ids. It does not forward unselected results, split oversized results, truncate them, or summarize them. `context_read` returns complete snapshots addressed to the calling participant conversation, in requested order. Artifact grants prevent another conversation from reading them.

`magi_start` and `magi_deliberate` return immediate receipts. The arbitrator ends its provider turn while participants deliberate. It must not poll, sleep, or hold a waiting tool call. A durable queued notification wakes the owner when the complete turn is persisted; `magi_get_turn_result` acknowledges delivery and returns canonical evidence. Parsed evidence is returned once as structured content; raw provider text remains durable for recovery and is returned directly when parsing fails. Wrappers exposing both MCP content and structuredContent must emit only structuredContent to avoid duplicating large results.

The arbitrator records every participant's semantic stance with evidence. It accounts for discrete external findings, proposals, dissent, actions, verification, and required cleanup. It follows the server's transition before responding. Recovery tools are for explicitly truncated/lost results or compaction/session recovery, not normal polling or convenience. Direct database, server-log, or provider-transcript inspection is not the Magi recovery interface.

## Consensus, proposals, and actions

Turn 1 is independent: participants do not see peers' identities, weights or responses. Each provides a recommendation, rationale, assumptions, risks, confidence, and optional proposals. The arbitrator classifies every contribution as supports, opposes, or unclear against the exact question and candidate. The server validates ids and computes support from this turn only.

Later turns include the immutable initiating instruction, focused objective, current candidate fingerprint, current participant evidence, active proposals, compact closed-proposal digest, relevant arbitration, action records, unresolved disagreements, and new artifact manifests. A candidate fingerprint covers normalized candidate content and durable action state. Any material candidate change or action record requires a fresh matching-fingerprint ballot. Approval of an earlier candidate cannot silently authorize new claims, technologies, conditions, costs, risks, or actions.

A ballot that conflicts with its rationale is interpreted against the exact candidate and question. A remaining material ambiguity becomes unclear with zero approval weight and a focused clarification question to the whole electorate. Fresh current-turn ballots decide it. The server never invents a semantic interpretation from one structured field.

Proposals have stable ids derived from exact deterministic normalization; semantic similarity does not merge them or transfer votes. New/revised proposals must be shown to every participant in a later turn, including optional proposals. Creating a proposal is not a vote. Approval and explicit rejection are computed separately using the fixed threshold; failures, omissions, ambiguity, and abstention add no weight to either side.

An evaluated proposal reaching neither threshold receives one focused reconsideration, then becomes unresolved if still undecided. A fan-out whose settled weight cannot reach threshold does not consume an evaluation opportunity. Accepted, rejected, unresolved, and superseded proposals leave the active matrix. Accepted proposals must be incorporated or explicitly omitted and then confirmed by a fresh candidate ballot. Rejected proposals need no extra confirmation. Optional unresolved/rejected proposals do not independently block otherwise valid candidate consensus.

Independently approved but incompatible proposals form one exclusive decision set. Prior independent adoption does not authorize conflicting actions. Each participant chooses one option or neither, and at most one can reach threshold. A persistently split set becomes unresolved after its focused reconsideration. The ordinary candidate ballot still decides the resulting conclusion.

Every arbitration supplies terminalProposalDigestUpdates. The service merges arbitrator-authored summaries and rejects missing, duplicate, unknown, active, or aggregate-oversized entries without rewriting or truncating them. Recovery can page terminal proposals to repair a missing digest. Closed evaluation matrices remain durable but are not resent in later prompts.

The authoritative transitions are actions-required, consensus-reached, continue, and turn-limit-reached. Issued actions require independent user authority. Action records classify exact issued batches as completed, not-completed, or unknown. Unknown outcomes require reconciliation and are never automatically replayed. A required failure or unforeseen consequence returns to participants; an optional action may be omitted with a recorded explanation. Recording actions changes the fingerprint, so actions-required never transitions directly to consensus-reached. A finite limit still permits already-approved authorized actions, then ends without consensus if no confirmation turn remains.

## Participants and lifecycle

Participant ids derive from delegated-task command ids, allowing evidence addressing before child creation. Turn 1 uses `delegated_task.request`; ordinary delegated-task completion delivery is disposed because Magi delivers one complete electorate result. Later turns, retries, structural repair, and compaction use deterministic queued messages to the same participant conversation. The initiating-task envelope repeats after compaction. Every participant has the owner's runtime and interaction modes.

The service waits on persisted terminal run events, reads physical dispatched-run results, and tracks their token usage. Each logical participant turn allows at most one transient retry and one distinct structural repair. Raw malformed structure remains evidence rather than erasing useful text. Full prompts are preferred; native compaction is requested when supported and needed. Free-form evidence compression is a fallback that preserves structured decisions and is marked durably. Oversized selected tool activities are rejected before dispatch.

The owner retains ordinary composer and steering behavior. Its operational pending-work marker keeps it Waiting between provider turns and prevents a delegated owner's task from completing before arbitration and the final answer. Approval/input waits, explicit pause, and terminal states clear the marker. Ordinary Stop pauses Magi even after the provider turn has settled. Forks do not inherit the marker.

The marker's computed `magi:<runId>` monitor is operational state, excluded from background-work presentation on every client. It must not produce an extra conversation banner, floating status/action control, or details-sheet entry. Participants retain ordinary subagent cards, work banners and owning-conversation Lineage. Generic MCP activity such as `magi_start`, and generic system notifications that carry completion/control continuations, remain visible and functional. These are normal tool and notification UX, not a Magi run panel. The old dedicated timeline box and placement metadata are already removed; this presenter correction adds no persisted UI data and needs no migration beyond069.

Ordinary composer Stop remains available on web/desktop and mobile for unfiltered completion-holding background work even when no provider run is active. The existing web thread.stop keybinding uses the same availability gate. In that state clients dispatch the existing thread-level interrupt without a runId and retain destination permission checks; the server selects the target run, including when a newer run is queued. Existing runless provider interrupt behavior is preserved. This keeps Stop reachable while the special Magi status/action presentation stays absent. A non-empty draft retains ordinary Send behavior.

Completion delivery and protocol repair have distinct durable identities. Pause withdraws an unstarted notification and holds results. Resume offers held results again. Reading from a newer user turn acknowledges evidence and cancels a redundant queued wake. Stable delivery ids repair a crash between enqueue and persistence without duplicating the wake.

Interrupted initialization/deliberation fails at startup and cleans up participants; the service does not reconstruct an in-flight collector. Other states recover durably. Resuming a paused deliberation whose live fiber was lost starts a new Magi turn. V2 continuation of a participant independently does not become evidence for a failed Magi turn. Cleanup is retried after interrupted terminal cleanup.

## Persistence and integration

The final standalone migration is 069_MagiProjections after upstream 068. It keeps four tables: magi_runs for operational snapshots and owner/replay/recovery queries, magi_run_participants for participant policy, magi_context_artifacts, and magi_context_grants. Protocol snapshots retain configuration, members, turns, raw settlements, arbitration, proposals, decision sets, actions/reconciliation audit, pending batches, completion delivery, recovery state, and initiating context. These remain necessary without a panel.

The migration removes arms, ancestor audiences, unused V1 projection_magi_* tables, duplicate presentation-only SQL columns, generated titles, timeline placement ids, obsolete participant role configuration and snapshot values, and hydrated display fields from snapshots. Operational protocol and evidence are preserved. The copied active-installation Magi fixture contains 137 V2 runs; cleanup preserves all of their protocols and grants and passes integrity checking.

The last isolated copy of the active installation has published fork migrations through 080_DropUnusedV1Projections. Its ledger is incompatible with the standalone branch numbering. A later integration must preserve every published id/name and append this branch's cleanup body as the next available fork migration, previously planned as 081, rather than renumbering/replaying the standalone 069 or re-running the older 072/073 Magi migrations. This task does not integrate, rebuild, restart, or migrate the active installation. The user will rebuild later.
